## Context

See proposal.md - Why. Constraints that shape this design:
- Must run on any machine (Windows, macOS, Linux) with no paid service and no public network endpoint.
- Claude Code's only supported extension points for this are: (a) hooks (`Stop`, `Notification`, etc. — shell commands invoked with a JSON payload on stdin), and (b) headless/print mode (`claude -p "<prompt>" --resume <session-id>`), which continues an existing session's transcript non-interactively and exits.
- Confirmed via official docs: the `Stop` payload includes `last_assistant_message` (the complete response text) directly — no need to parse `transcript_path` ourselves, which the docs note is written asynchronously and can lag. The `Notification` payload includes `notification_type` (an enum: `permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`, `auth_success`, `elicitation_*`) and `notification_message`. `Stop` has no matcher (fires every time); `Notification`'s `matcher` filters on `notification_type` at the settings.json level.
- Hook `command` entries accept an `args` array (exec form, no shell) - this is how per-account `owner`/`label` reach the hook script (see Decision below), and it avoids cross-platform shell-quoting issues entirely.
- A hook script that exits with code 2 tells Claude Code "don't stop" (the conversation continues) - this is the one exit code our hook must never produce, intentionally or by accident.
- Several Claude Code accounts can run on the same machine (separate `CLAUDE_CONFIG_DIR`s or OS-level separation); each needs its hooks wired independently, but they should all feed one bridge instance.
- Ownership is a property of a Claude Code account (which owner it was installed for), not of a physical machine — two owners can be installed on the very same computer as long as each has their own account wired in by the installer.
- Telegram gives every bot exactly one conversation thread per (bot, Telegram account) pair — there is no such thing as "two chats" between the same person and the same bot. Multiple simultaneous "conversations" therefore means multiple distinct Telegram accounts (one per owner), not multiple threads from one account.

## Goals / Non-Goals

**Goals:**
- One small, dependency-light Node.js service per machine that is the only thing talking to Telegram.
- Notifications and replies work without opening any inbound port or provisioning a tunnel.
- Safe by default: registration gates all inbound control, and secrets never enter version control.
- Simple routing: most-recent session by default, one prefix syntax to override — no command language to learn.
- Multiple people can share one bridge instance, each strictly isolated to their own Claude Code sessions, via invite-code registration.

**Non-Goals:**
- Supporting messaging apps other than Telegram in v1 (the proposal already covers why WhatsApp/unofficial clients were rejected).
- Controlling a live interactive terminal/PTY session directly.
- Visually separate conversation threads per project for a single owner (e.g. Telegram groups with Topics). The default and only v1 answer for "I have several of my own sessions" is one chat + `label:` prefix; Topics could be a later enhancement but adds bot-admin-in-group complexity not justified now.
- Encrypting the local session registry at rest in v1 (noted as a possible follow-up, not required now).

## Decisions

1. **Long polling, not webhooks.** Long polling needs only outbound HTTPS, so it works from behind home NAT/CGNAT with zero extra infrastructure. Alternative considered: Telegram webhooks, which need a public HTTPS endpoint (ngrok/Cloudflare Tunnel) running continuously — rejected for v1 because it adds a second always-on dependency for no benefit at this message volume; can be offered later as an opt-in mode.

2. **Bare `getUpdates` loop over `fetch`, not a full Telegram SDK.** Keeps the dependency tree tiny for a process that holds a bot token and can shell out to `claude`. Smaller supply-chain surface matters more here than developer convenience.

3. **Output capture via Claude Code hooks (`Stop`, `Notification`), not log-tailing or wrapping the `claude` binary.** Hooks are the officially supported extension point and deliver structured JSON per event with no change to how the user normally invokes Claude Code. Alternative considered: a shim on `PATH` replacing `claude` — rejected because it would miss any session started outside that shim (IDE integration, existing aliases, other machines' shells).

4. **Input delivery via headless resume (`claude --resume <id> -p "<text>"`), not keystroke/PTY injection.** Headless resume is a first-class, cross-platform, officially supported mode that operates on the session's transcript rather than a live terminal, so it cannot corrupt or race with an interactive session. Alternative considered: injecting synthetic input into the session's controlling terminal — rejected as OS-specific and fragile (Windows in particular has no simple equivalent).

5. **Session registry as a local JSON file, not a database.** Matches the real scale (a handful of concurrent sessions on one machine), needs no extra runtime dependency, and is trivially inspectable while debugging. Writes are per-session-id keyed and last-write-wins per key, which is enough at this concurrency level.

6. **Routing precedence: reply-based match, then `<label>: ` prefix, then most-recent.** Telegram's native "reply to this message" gesture is the primary UX — tap-and-hold the bot's last notification for project1 and reply to it, and the answer goes straight to project1, with zero prefix-typing. The `<label>: ` prefix remains as the way to start a *new* thread of conversation with a specific session (nothing to reply to yet), and most-recent is the last-resort default. Alternative considered: prefix-only (no reply support) — simpler to implement but worse in practice once more than one session is live, since remembering to type the right label every time is exactly the friction "algo mais simples" was pushing back on.

7. **The Telegram allowlist is the single trust boundary.** It is the only thing standing between "anyone who finds the bot" and "a message that gets executed as a Claude Code prompt on this machine," so it is enforced at the gateway layer (`telegram-gateway`) before any routing or session logic runs, not deep inside `input-relay`. The bot token lives in a local, git-ignored config file (e.g. `.env` / `config.local.json`), never inside `openspec/` or any committed file.

8. **`enabled` is toggleable from Telegram itself (`/on`/`/off`), not just local config.** Both paths read/write the exact same boolean, so gateway enforcement logic never forks based on where the toggle came from — the chat command handler is just another writer of the same flag, gated by the same allowlist check as any other inbound message.

9. **Standalone binaries via Node.js Single Executable Applications (SEA), not `pkg`/`nexe`.** SEA is built into Node core (Node 20+), so it adds no third-party build-tool dependency to something that ends up holding a bot token and shelling out to `claude` — smaller supply chain for a security-sensitive artifact. It also embeds the Node runtime into the produced binary, so a target machine needs nothing pre-installed. Alternative considered: requiring users to install Node.js and run the bridge as a plain npm package/CLI — rejected because it breaks the ≤2-click, zero-prerequisite bar on a machine that isn't already a dev box.

10. **GitHub Actions builds and publishes the three OS binaries on each tagged release.** End users always install from a built release artifact on GitHub Releases, never by cloning the repo and building it themselves — keeps "ready to version on GitHub" and "install on any machine in ≤2 clicks" consistent instead of in tension.

11. **First-run setup wizard collapses config + hook wiring + service registration into one guided flow.** Running the executable is interaction #1; entering (or confirming an already-saved) bot token is interaction #2; everything else — writing config, merging hooks into the detected Claude Code account(s), registering the background service — happens automatically in that same run.

12. **Multi-owner sharing via one-time invite codes, not an external identity provider.** The operator generates a code out-of-band (any channel) and the invited person redeems it with `/register <code>` from their own Telegram account. No email/OAuth/user database — matches "free and simple," and the invite code is itself the only thing that needs to be kept secret in transit.

13. **Ownership scoping happens in `session-registry`, not by filtering the Telegram allowlist per-message.** `telegram-gateway` only answers "is this chat registered at all?" (cheap, same check regardless of owner count); `session-registry` then narrows "which of *this owner's* sessions could this message mean?" This keeps the two concerns separate: gateway = authentication, registry = authorization/isolation.

14. **Same-machine multi-owner is just multiple accounts, each installed separately.** The installer already runs per Claude Code account (§5 of proposal); adding a second owner on the same physical computer is: run the installer again for a second account (a second `CLAUDE_CONFIG_DIR`/OS profile), and during that install associate it with the newly registered owner. No per-machine concept exists anywhere in the design — only per-account.

15. **`output-relay` is the single path that ever delivers a successful turn's result; `input-relay` never relays on success.** Without this, a message the bridge itself triggered would produce two Telegram messages for one turn: one from `input-relay` capturing the headless process's stdout directly, and one from the same turn's own `Stop` hook firing through `output-relay` as it does for every turn. Making `output-relay` the only success-path sender removes the duplicate entirely; `input-relay` only speaks up when the headless call fails *before* a `Stop` hook could fire (crash, non-zero exit, timeout), since in that case `output-relay` has nothing to relay.

16. **Outbound messages are tracked (message id → session id) specifically to support reply-based routing, and are pruned, not kept forever.** Only recently-sent messages are realistically ever replied to, so the tracking table keeps a bounded window (e.g. the last N messages or last few days) rather than growing without limit.

17. **Only `owner` is baked into the hook command's args at install time; `label` is derived live from the session's own `cwd`, not baked in.** `owner` is fixed per account (that's what "account" means here), so it belongs in the static install-time args (e.g. `args: ["--owner", "caio"]`). `label`, however, needs to vary per *project*, and Claude Code hooks are typically wired once per account/user (`~/.claude/settings.json`), covering every project that account ever opens — a label baked in at install time would give every project under that account the same label, breaking exactly the "projeto1 vs projeto2" distinction the routing design depends on. Deriving `label` from `path.basename(cwd)` inside the hook handler itself, per event, means one account install automatically gives each project its own sensible label with no extra step. `--label` is still accepted as an optional override (e.g. for a project whose folder name isn't a good label), just never required.

18. **`Notification` is wired with a broad (or absent) matcher; granularity filtering happens in our own code against `notification_type`, not in settings.json.** If the matcher itself encoded the default/verbose split, changing `granularity` in config would require reinstalling hooks to take effect. Filtering in code means the toggle is live immediately. The cost is our script is invoked for `Notification` types it may end up discarding - negligible given fail-open, sub-second execution.

19. **The hook script always exits 0, even on internal failure.** Exit code 2 specifically tells Claude Code not to stop, which this bridge must never trigger by accident; failures are logged to a local `bridge.log` instead of surfacing through the exit code.

20. **One entry point (`bin/bridge.js`) serves both the CLI and the hook handler, via a `hook` subcommand, instead of two separate scripts.** Confirmed while researching packaging (Fase 9): a Node.js Single Executable Application embeds exactly one main script, so a separately-invoked `bin/hook.js` could never be packaged alongside the CLI in one binary. Consolidating before packaging means the installer's hook `command`/`args` only need to change from `node bridge.js hook --owner X` (source mode) to `<binary> hook --owner X` (packaged mode) — everything else about hook wiring stays identical.

21. **The SEA build bundles everything to CommonJS with esbuild first, rather than feeding the ESM source straight to `--experimental-sea-config`.** Researched directly against the official docs while implementing: ESM entry-point support in Node's SEA tooling only landed very recently (a PR merged 2026-02-13) and isn't something a build reliably running on whichever Node version a contributor or CI runner happens to have should depend on. Bundling to CJS with esbuild (a build-time-only devDependency, never shipped) sidesteps the whole question. This surfaced a real bug: `bin/bridge.js` used `path.dirname(fileURLToPath(import.meta.url))` to locate itself, which throws once bundled (esbuild leaves `import.meta` empty in CJS output) - confirmed by actually running the built binary, which crashed on startup before the fix. Fixed by wrapping that call in a try/catch and treating the failure itself as the signal "this is the packaged binary" (only bundling empties `import.meta`; real ESM source never does), falling back to `process.execPath` for anything that used to need the script's own path.

- **Telegram outage or rate limiting** → the bridge is a best-effort notification/remote-control channel, not a control-plane guarantee; Claude Code sessions keep working normally whether or not the bridge is reachable.
- **A hook script failing or throwing** → hook scripts must fail open: never block, delay, or crash the actual Claude Code turn they're attached to, and log failures locally for diagnosis instead of failing silently.
- **Bot token leaked** → the chat-id allowlist still blocks an attacker from being treated as an authorized sender even if they obtain the token; the token should still be rotated if this happens, and docs will say so explicitly.
- **Concurrent hook events from multiple accounts writing the registry at once** → per-session-id keyed writes avoid clobbering unrelated entries; same-key races are acceptable to resolve last-write-wins given the low event rate.
- **Headless `--resume` inheriting session state that assumes interactive approval** → anything that would normally require an interactive permission prompt should surface as a `Notification` back through the same relay rather than hanging the headless call.
- **Node SEA is a relatively young feature (stable since Node 20, but still evolving)** → pin the embedded Node version per release (the CI runner's own Node, via `actions/setup-node@v4` with `lts/*`), test the built binary on real Windows/macOS/Linux before each release, and keep the plain npm-based CLI path documented as a fallback for advanced users if a packaged binary ever misbehaves on a specific OS/architecture.
- **This machine could only build and verify the Windows binary** → the macOS and Linux binaries are produced by the same script running on GitHub Actions' `macos-latest`/`ubuntu-latest` runners (see `.github/workflows/release.yml`), which is also where they get their first real verification; this is tracked as an open item, not silently assumed to work.
- **First-run wizard collects a secret (bot token) interactively** → the wizard writes it directly to the local, git-ignored config file and never logs it, echoes it back in full, or transmits it anywhere other than Telegram's own API.
- **Owner-scoping bug lets one owner's message reach another owner's session** → the scoping filter is applied unconditionally before the existing most-recent/prefix routing logic runs (never bypassable by prefix or by having zero sessions of one's own), and is regression-tested explicitly with two owners registered on the same machine.
- **Invite code intercepted in transit (e.g. read over someone's shoulder in a chat app)** → codes are single-use and consumed atomically on first successful `/register`, so an intercepted code that's already been redeemed is worthless; codes should still be sent over a reasonably private channel and can be left unconsumed/regenerated if leaked before use.
- **Double-sending a turn's result (once from `input-relay`, once from `output-relay`)** → eliminated by design: `output-relay`'s `Stop` hook path is the only success-path sender (Decision 15); regression-tested explicitly so this can't silently regress.
- **Unbounded growth of the outbound-message-tracking table** → bounded/pruned window (Decision 16); a reply to a message old enough to have been pruned simply falls back to prefix/most-recent instead of erroring.

## Migration Plan

Greenfield project — no existing users to migrate. Recommended rollout order (reflected in tasks.md): ship `telegram-gateway` + `session-registry` + `output-relay` first (read-only notifications, zero risk of unwanted actions on the machine), validate for a few days of real use, then add `input-relay`. `installer` ships alongside the first usable slice so the whole loop is installable end to end.
